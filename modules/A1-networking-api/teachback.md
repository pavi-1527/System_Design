# A1 Teach-back

## Prompt

A mid-level engineer on your team is about to build the "send money to an external account" endpoint. They have never
thought about what happens between a client's tap and the core banking system, and their plan is "the app retries on
error, it's fine".

Explain to them, in your own words, **how a request from the mobile app reaches the transfers service, why retrying
a transfer can move money twice, and how to make the endpoint safe to retry end to end** — including what the client,
the server and the core-banking adapter each have to do.

Form: written, 400–800 words, may include one diagram (Mermaid or a sketch). No copying from the unit text: if a
sentence from the course appears verbatim, the evaluator will ask you to rephrase it. Write for that engineer, not
for an examiner — concrete beats complete.

## Evaluator checklist

Must-hit (all required for pass):
- [ ] Explains that a timeout is **ambiguous**: the server may not have received the request, may still be
      processing it, or may have succeeded with the response lost — so a blind retry can duplicate the transfer.
- [ ] States that `POST` is not idempotent by HTTP semantics and that idempotency must be added by the API
      (an idempotency key), not assumed.
- [ ] The key is **generated by the client once per user intent** and **reused on every retry** of that intent (a new
      key per attempt gives no protection).
- [ ] The server **reserves the key atomically before doing the side effect** (one conditional write; "check then
      act" is a race) and keys are **scoped** per client/tenant.
- [ ] Describes the outcomes: completed → **replay the stored response**; still in flight → **409 (or wait)**;
      same key with a **different request → reject (422)**.
- [ ] Carries idempotency **downstream**: the adapter passes a key/reference to core banking (or reconciles), because
      the server can crash between the core's success and recording it.

Should-hit (at least 4 of 7):
- [ ] Describes the request path in a sentence or two with at least DNS/edge, load balancer, service, adapter — and
      where the extra retries could come from (client, gateway, adapter).
- [ ] Retry policy: only one layer retries, exponential backoff with **jitter**, a retry budget, and timeouts ordered so
      inner hops give up first.
- [ ] Request **fingerprint** (method, path, body) explained as the way to catch key reuse.
- [ ] **Leases** on in-flight records so a crashed worker can't wedge a key, and why that requires downstream
      idempotency.
- [ ] A position on caching **5xx** responses (don't store if the handler guarantees no effect; store/replay if partial
      effects are possible) with the reason.
- [ ] Retention/TTL ≥ the client's retry window, with a rough storage estimate.
- [ ] Mentions where the record lives (same DB transaction as the transfer, or Redis with its failover caveat) and why.

Red flags (any one = revise):
- [ ] Claims retries are safe because "HTTP/TCP guarantees exactly-once delivery" or because the server "can tell
      whether it already processed the request" without a key.
- [ ] Proposes deduplicating on request content (same amount/accounts/time window) as the mechanism.
- [ ] Puts the duplicate check *after* calling core banking, or uses a non-atomic check-then-insert without noticing
      the race.
- [ ] Has the server generate the idempotency key, or the client generate a new key per retry.
- [ ] Replays a stored response for a request with a different body/path under the same key.
